# Plan: exports and feeds (E-1 to E-4)

2026-10-25. Spec: `docs/specs/exports.md`, accepted 2026-10-24 with its five
decisions. Branch: `feature/shopify` (the exports close phase 16, after S2b).

**Done the same day** (ADR 0069; `docs/delivery-plan.md`), with three changes to the
design below: the feed lives outside the OpenAPI document (its paths are `/api/` only,
and Merchant Center reads Google's shape, not ours); the accountant's file names an
order by the reference the backoffice shows; and its headers are in the reader's
language, so the contract suite asks column names by culture. E-3's import by
Shopify's own importer is left to the author.

## What the code says, read today

- **A project of adapters may not reach a domain**: `An_adapter_never_reaches_a_domain`
  computes every `*.Domain` namespace of the contexts and holds `Solution.Adapters`
  (today Shopify) to none of them. Exports joins that list, so it cannot read a
  `Product` or an `Order`. `IProductCatalogReader` and `IOrderReader` hand out
  aggregates: **each context gets a read port of values for its export**, implemented
  inside the context, where rendering an attribute or a tax line is already known.
- **Availability is already a port of values** (`IAvailabilityReader`, SKU → units
  that can still be sold).
- **The storefront's address** is configured for UCP (`Ucp:StorefrontUrl`, set by the
  AppHost); pictures are served at `/api/images/{id}` (UCP builds the same URL).
- **Audit is a dispatcher decorator over commands only.** An export that must leave
  an audit row (who exported what) is a command; one that must not (Merchant Center
  fetching the public feed daily) is a query.
- **No CSV library**, and none is added: writing RFC 4180 is twenty lines.

## Design

**The outbound port** (E-1), in `ElGuerre.Tendero.Exports`:

- `IExportFormat<TRow>`: a keyed adapter that writes a list of rows of one kind
  to a stream — `Format` (its key), `ContentType`, `Extension`, `WriteAsync(rows,
  ExportWriting, stream, ct)`. `ExportWriting` carries the culture (which picks the
  CSV separator, decision 4). One registration per format per kind of row, no `if`
  in a slice: the slice asks `IExportFormats.Get<TRow>(format)`.
- The rows are Exports' own records: `FeedItem` (E-2), `ProductForAnotherPlatform`
  (E-3), `OrderLineForTheBooks` (E-4).
- **The contract suite** `ExportFormatContractTests<TRow>`: every row given comes
  out, in order; money in the currency's decimals and never in a culture's digits
  (a comma never appears inside a number in a TSV, `12.50` not `12,5`); the file
  reads back with the format's reader; an empty list writes a file with its header.
  Each format supplies rows and how one row reads back as cells.
- `Csv` (writer and reader, RFC 4180, a BOM when the reader is a person) lives in
  Exports; the tests read back through the same reader, and through a second,
  independent split in the contract suite for the quoting.
- `An_adapter_never_reaches_a_domain` covers Exports (`Solution.Adapters`), and an
  architecture test names it as not a context.

**E-2, the product feed.**

- `Catalog.Ports.ICatalogueExport` → `ExportedProduct` values (code, on sale or not,
  names, descriptions and slugs per culture, brand, category branch per culture,
  pictures with alt text, attributes and variant options rendered per culture,
  each variant's SKU, barcode, price, picture). Implemented in Catalog.
- Slice `Exports/Features/ProductFeed`: a **query** (no personal data; decision 5:
  public), `GET /feeds/google/{culture}.tsv`, `AllowAnonymous`, products on sale
  only, one row per variant grouped by `item_group_id` = the product's code;
  `availability` from `IAvailabilityReader`; `google_product_category` from
  `seed/google-categories.sample.json` (our category code → Google's taxonomy id,
  the nearest ancestor's when a category has none; proposed by me, approved by the
  author on 2026-10-28 as the Shopify mapping was); the answer counts the rows without one in
  a header (`X-Feed-Uncategorised`).
- The adapter `google-merchant`: tab-separated UTF-8 with Google's attribute names,
  checked against Google's product data specification on the day.
- The counter `tendero.exports.generated` (`export.kind`, `export.format`, rows), in
  the tracking plan.
- The backoffice: a *Feeds and exports* card on the catalogue screen with the feed's
  two URLs to copy and open.
- Test over the seed: every required field present on every row, variants grouped.

**E-3, Shopify's product CSV.**

- Slice `Exports/Features/CatalogueForAnotherPlatform`: a **command** (audited),
  `POST /api/exports/catalogue?format=shopify-csv&culture=es`, Shopkeeper, every live
  product (Draft as `draft`, on sale as `active`).
- The adapter `shopify-csv`: Shopify's product CSV columns (handle, title, body HTML,
  vendor, type, tags, published, options 1–3 name and value, variant SKU, barcode,
  price, inventory quantity, image src and position and alt text, variant image,
  status), first row of a product carrying its fields, the next ones its variants and
  pictures.
- The round trip from the other side: the seed exported, imported by Shopify's own
  product importer into the lab store, and compared — Shopify's CSV import is a
  screen in the admin, with no API, so that step is the author's, with a checklist.

**E-4, orders for the accountant.**

- `Ordering.Ports.IOrderExport` → `ExportedOrder` values for a period (the shop's
  days, ADR 0046): number, day, status, the billing party (name, tax id if any,
  country), each line with SKU, name, quantity, unit price, discount, tax class and
  rate, tax and total.
- Slice `Exports/Features/OrdersForTheBooks`: a **command** (audited: who exported
  which period), `POST /api/exports/orders?from=…&to=…&culture=es`, Shopkeeper.
- The adapter `csv` for the reader's culture: `;` and a decimal comma for es, `,` and
  a decimal point for en — numbers as numbers so the spreadsheet sums them — UTF-8
  with a BOM.
- Tests: the export summed equals the orders' totals; after a customer's erasure the
  export holds nothing of them but what the order froze for the invoice (the six
  years' blocking): no email, no phone.

## Order of work

E-1 → E-2 → E-3 → E-4, each test first, each with its docs. OpenAPI and the frontend
types regenerated after E-2 and again after E-4. Stryker is phase 16's close, after
the exports: not in this plan.

## Calls made here, for the author to check

- The feed is a query and the two downloads are commands: the public feed would
  write an audit row on every fetch Merchant Center makes.
- The feed's price is the catalogue's, as the product page shows it: Merchant Center
  refuses a feed whose price differs from its landing page.
- The Google category mapping is proposed, not approved: the feed works without it
  and counts what has none.
